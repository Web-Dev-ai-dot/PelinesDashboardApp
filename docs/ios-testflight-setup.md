# iOS staging build setup

## Current scope

The `ios-staging-build` workflow compiles an **unsigned release device app** on
Codemagic. It does not create certificates, sign an IPA, upload to Apple, or
distribute through TestFlight. It has no automatic triggers or publishing block.
Build-only validation is not a TestFlight-ready signed IPA.

- Bundle ID: `com.tkr.pelinesadmin` (RunnerTests: `.RunnerTests`).
- Display name: **Pelines Admin**.
- Version: Flutter `1.0.0+1`; retain Flutter's plist substitutions.
- Deployment target: **iOS 15.0**; iPhone and iPad supported.
- Native dependencies: **Swift Package Manager**, not a CocoaPods migration.
- Printer: manually entered IP/port, Dart TCP + ESC/POS, normally port **9100**.
- `NSLocalNetworkUsageDescription` explains printer connection/printing.
- `NSPhotoLibraryUsageDescription` explains choosing a menu product photo.
- No Bonjour services, multicast entitlement, ATS exceptions, camera/microphone
  permissions, Epson SDK, or background printing capability is added.
- A small STAGING strip appears on every route only for `APP_ENV=staging`.

## First manual Codemagic run

1. Give Codemagic access to this GitHub repository. Select configuration from
   `codemagic.yaml` on `main`, then workflow `ios-staging-build`.
2. Create an environment group named **pelines_staging**, available to this app.
   Set the following variables (mark the client key secure/encrypted):

   | Variable | Value/source |
   | --- | --- |
   | `APP_ENV` | `staging` |
   | `API_BASE_URL` | `https://pelines-api-staging.aiwithtalha.com/v1` |
   | `SUPABASE_URL` | `https://qrtuwjpofwtefueqtokp.supabase.co` |
   | `SUPABASE_ANON_KEY` | Staging anon/publishable client key from approved secure configuration |

3. Start the workflow manually on the intended main commit. It selects a macOS
   M2 worker, Flutter **3.47.2**, and Xcode **26.6**. No Apple credentials are
   required for this unsigned run. Review any separate pre-existing Codemagic
   UI workflows/webhooks; this YAML contains no publishing actions.
4. The workflow resolves the locked Dart packages, analyzes/tests, generates an
   ignored JSON configuration with Python's JSON encoder, regenerates iOS
   configuration on macOS, resolves SwiftPM, and runs
   `flutter build ios --release --no-codesign` with the JSON dart-defines.
   The JSON is deleted on shell exit, including ordinary build failures.
5. Success means SwiftPM/native plugins, Flutter release code, plist, and assets
   compile into `build/ios/iphoneos/Runner.app`. The downloadable artifact is
   `unsigned-pelines-admin-staging.zip`. It is **not an IPA** and cannot be
   installed with TestFlight. Archive validation/signing and hardware behavior
   are still unproven.

Never commit `.env.staging.json`, generated xcconfig/plugin files, keys,
certificates, profiles, or build products. Do not print configuration values or
use verbose build logging to expose dart-defines. The client key is necessarily
embedded in the compiled app; encrypted CI storage does not make it a server
secret. Never use a service-role/secret key. The generator rejects wrong URLs
and non-anon/wrong-project legacy JWTs; publishable-key ownership must be
verified when setting the secure group.

The existing Windows-generated files are ignored. Do not hand-edit their paths
or copy them to CI. All current native plugins declare SwiftPM support; do not
add a Podfile unless a specific macOS dependency failure demonstrates a need.
The first Mac run must also check native dependency/privacy-manifest warnings.

## Icon source

`assets/branding/pelines_admin_icon.png` is the approved 1254px source. The iOS
catalog is generated by `python3 tools/prepare_ios_icons.py` (Pillow required).
It crops 40px of outer background on each edge to remove the baked-in black
rounded-corner matte, preserving the P and circular artwork. Every declared
size is RGB/opaque, including 1024px marketing artwork. Android icons and the
source remain unchanged. No redesign or new artwork is involved.

## Later signing and TestFlight (not enabled)

After a successful unsigned build and explicit authorization:

1. Confirm TKR's Apple Developer membership/team, agreements, bundle-ID ownership,
   explicit App ID, and App Store Connect app record (name, language, SKU).
2. Configure Codemagic's Apple integration using issuer ID, key ID, and private
   `.p8` with appropriate permissions. Supply the Apple Team ID and distribution
   certificate/private key/profile, or authorize Codemagic automatic signing.
   The API `.p8` and signing certificate's private key are different credentials.
   Keep them in Codemagic secure storage, never YAML/Git.
3. Use a new increasing build number and a separate signed
   `flutter build ipa --release` workflow with the same staging defines and
   App Store export configuration. Address export compliance and archive checks.
4. Only then authorize upload to App Store Connect and internal TestFlight
   distribution. Do not enable App Store release publishing. Create an internal
   tester group with eligible App Store Connect users.
5. Use an iPad mini supporting the current TestFlight app (currently iPadOS 16+,
   mini 5th generation or newer). Install, confirm STAGING, login, verify admin,
   locations, Today, and Menu using read-only actions.
6. On the printer's reachable LAN, select Network Epson/ESC-POS, enter its IP and
   port 9100, and use Test Connection. Grant Local Network access; retry the
   connection test if the first prompt outlasts the four-second timeout.
7. After separate physical-test authorization, enable local printing and issue
   one Test Print. Verify one ticket, accents, wrapping, feed/cut, submitted queue
   state, and no duplicate after relaunch. Submitted is not physical confirmation;
   ambiguous delivery stays unknown and must not be blindly retried.

No Accept/Cancel/refund, menu upload, email, or other business mutation belongs
to this smoke test. Android-only foreground alert sound remains best-effort;
its missing iOS channel is caught and does not block printing.
